# Architecture

Generated: 2026-06-07

## System Shape

This is a two-surface service desk application:

- `backend/`: FastAPI application that owns Phoenix ERP access, run lifecycle,
  WebSocket streaming, SSH execution, deterministic command safety, LLM/tool
  orchestration, audit logging, and local mock ERP support.
- `frontend/`: React/Vite technician console that consumes backend REST and
  WebSocket contracts for ticket intake, run control, approvals, terminal output,
  hypotheses, decisions, and activity review.

The app has no app-owned relational database. Durable state is split between the
external Phoenix ERP and append-only JSON/JSONL files under the configured audit
directory.

## Entry Points

- `backend/app/main.py`: FastAPI app factory/lifespan, `/health`, REST router, and
  WebSocket router composition.
- `backend/app/api/routes.py`: REST API under `/api` for tickets, customer system
  lookup, active run discovery, resolution lookup, run creation, shell sessions,
  stop, and activity submission.
- `backend/app/api/ws.py`: `/ws/runs/{run_id}` event stream plus inbound
  technician actions: approvals, decisions, hypothesis steering, terminal input,
  resize, activity submission, and STOP.
- `backend/app/mock/phoenix.py`: offline Phoenix-compatible FastAPI app for local
  development and client tests.
- `frontend/src/main.tsx` and `frontend/src/App.tsx`: React router entry for
  ticket list, ticket detail, and run workspace pages.

## Module Boundaries

### Backend

- `app/config.py`: environment-backed settings, model names, audit directory,
  replay/retention limits, and per-ticket SSH key selection.
- `app/models.py`: broad shared kernel for Phoenix DTOs, internal run state,
  hypotheses, events, and request schemas.
- `app/erp/client.py`: Phoenix anti-corruption layer using `httpx`, bearer auth,
  retries, timeout handling, and Pydantic validation.
- `app/runs/manager.py`: central run aggregate, event replay, approvals,
  decisions, hypothesis selection, terminal PTY lifecycle, run registry,
  per-ticket supersede locks, garbage collection, and resolution lookup.
- `app/runs/resolutions.py`: ticket-keyed durable solution records.
- `app/agent/*`: continuous tool-calling LLM session, prompt/tool schemas, recon,
  investigation loop, fix proposal, decision requests, finish/activity drafting,
  and context compaction.
- `app/agent/tools.py`: command execution choke point. Every agent command and
  legacy one-shot manual command passes through safety, approval, SSH, redaction,
  audit, and WebSocket terminal emission here.
- `app/safety/rules.py`: deterministic ALLOW/CONFIRM/DENY classifier and output
  redaction. The LLM is not in the security boundary.
- `app/ssh/runner.py`: asyncssh connection, command execution with timeout, and
  interactive PTY support.
- `app/audit/log.py`: append-only per-run JSONL audit log with redaction before
  persistence.
- `app/mock/phoenix.py`: local in-memory implementation of the Phoenix API
  contract for dev and tests.

### Frontend

- `src/api/client.ts`: manual TypeScript mirror of backend REST/WebSocket DTOs.
- `src/pages/TicketList.tsx`: ticket intake, filtering/sorting, and in-progress
  run discovery.
- `src/pages/TicketDetail.tsx`: customer report, customer system details,
  resolution display, run start, and plain SSH start.
- `src/pages/Workspace.tsx`: run state machine UI, WebSocket event handling,
  terminal, agent stream, approval/decision gates, hypotheses, and activity
  submission.
- `src/components/*`: focused widgets for terminal, approvals, hypotheses,
  decisions, run controls, markdown rendering, resolution view, and activity
  review.

## Primary Data Flows

1. Ticket intake:
   `TicketList` -> backend `/api/tickets` -> `PhoenixClient` -> Phoenix ERP.

2. Run start:
   `TicketDetail` -> `POST /api/runs` -> fetch ticket/customer system from Phoenix
   -> `RunManager.create_run` -> spawn `run_agent` task -> frontend opens
   `/runs/{run_id}` and subscribes to `/ws/runs/{run_id}`.

3. Command execution:
   Agent tool call or legacy terminal command -> `execute_command` ->
   `decide(command)` -> optional approval -> `SSHRunner.run_command` -> redaction
   -> audit JSONL -> `command.run` and `term.data` events.

4. Human gates:
   Backend emits `approval.request`, `decision.request`, or `hypotheses` events.
   The workspace sends the selected/edited/approved decision over WebSocket, which
   resolves the waiting `Run` future.

5. Resolution:
   `Finish` -> activity draft -> technician review -> `POST /api/runs/{id}/activity`
   -> Phoenix `create_activity` -> Phoenix status update (`DONE` for fixed,
   `PENDING` for not reproducible/escalation) -> `ResolutionStore.save`.

## Boundary Notes

- `Run` is the central aggregate and currently holds many responsibilities:
  phases, event history, terminal tail, approvals, decisions, hypotheses, activity
  state, SSH handle, audit log, and ERP reference.
- `agent/loop.py` is downstream of run lifecycle but imports and mutates `Run`
  directly. This is pragmatic for the hackathon, but it is the clearest boundary
  blur.
- `models.py` mixes external Phoenix contracts with internal run/event contracts,
  making the shared kernel broad.
- Frontend API types are manually mirrored from backend Pydantic models; contract
  drift is possible without generated schemas or contract tests.
